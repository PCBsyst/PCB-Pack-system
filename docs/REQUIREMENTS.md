# Certification Record Management System

## 업무 요구사항 및 데이터 구조 정의서

- 문서 상태: 현업 검토 초안
- 작성 기준일: 2026-08-30
- 적용 대상: 내부 자격인증 기록관리 업무
- 원칙: AI는 자격요건이나 승인 여부를 판단하지 않는다.

## 1. 문서 목적

이 문서는 자격인증 기록관리 시스템의 업무 범위, 사용자 역할, 핵심 데이터 구조, 상태 전환, 보완 및 재처리, 인증 사후관리, 보고서, 기존 데이터 이전과 운영 전환 기준을 정의한다. 개발 과정에서는 이 Markdown 문서를 원본 요구사항으로 관리하며, 현업 검토용 Word 문서는 같은 내용을 기준으로 생성한다.

## 2. 시스템 범위와 제외 범위

### 2.1 포함 범위

- 후보자 기본정보와 후보자별 전체 Job 이력 관리
- Job별 최초, 갱신, 등급변경, 범위확대 처리 회차 관리
- 서류검토, 인증심의, 인증정보 등록, 문서전달 기록
- 보완 요청, 재검토 및 재심의 회차 보존
- 인증 정지 및 인증 철회 사후관리 기록
- 신청 취소 기록
- 처리이력, 정정이력, 감사로그
- 내부 업무 알림
- Word, PDF, Excel, PowerPoint 보고서 출력 기반
- 기존 Google Sheet 전체 데이터 이전과 검토 대기 처리

### 2.1.1 기본 처리 흐름

신청서·계약서·증빙자료 접수 → 후보자 이력 및 Job No. 등록 → 1차 서류검토 → 인보이스 발행 → 입금 확인 → 인증심의 → 인증서 초안 → 인증번호 부여 → 인증서 PDF 발행·전달 → 완료

- 입금 확인 전에는 인증심의를 진행하지 않는다.
- Job에는 파트너사, 인증번호, 인증발행일, 만료일을 연결해 조회한다.
- 현재 Prototype은 인보이스와 PDF의 발행 결과만 기록하며 실제 자동 생성이나 결제 연동은 하지 않는다.

### 2.2 제외 또는 보류 범위

- AI의 자격요건 평가, 심의 추천, 승인 또는 불승인 결정
- 인증서 자동 발행
- 외부 신청자 Portal
- 결제 및 외부 업무 이메일 발송
- 원본 증빙문서 업로드 및 AI 문서 내용 분석
- 개인정보 마스킹은 후속 단계에서 적용
- 비밀번호 재확인과 전자서명은 후속 단계에서 검토

## 3. 사용자와 권한

### 3.1 시스템 역할

- 실무자: 모든 Job을 조회하고 인증업무를 처리할 수 있다.
- 관리자: 실무자 권한에 더해 사용자, 심의자 명단, 표준 사유, 날짜 계산 규칙과 정정 절차를 관리한다.
- 심의자: 시스템 계정을 만들지 않는다. 실무자가 전달받은 심의결과를 입력한다.

### 3.2 심의자 기록

- 심의자는 관리자가 사전 등록한 명단에서 선택한다.
- 명단에서 제외할 때는 삭제하지 않고 비활성화하여 과거 이력을 보존한다.
- 심의기록에는 실제 심의자와 시스템 입력자를 구분하여 저장한다.

### 3.3 로그인

- Supabase Auth 기반 이메일과 비밀번호 계정을 사용한다.
- 공개 회원가입은 제공하지 않는다.
- 관리자가 이메일 초대장을 보내며 사용자가 비밀번호를 직접 설정한다.
- 계정은 삭제 대신 비활성화하여 과거 처리이력의 사용자 연결을 유지한다.

## 4. 핵심 업무 단위

### 4.0 확정된 상위 구조

- 발행 분야는 `ISO 경영시스템 심사원`과 `K-Beauty 전문가 자격`으로 구분한다.
- 하나의 신청에는 인정과 비인정 세부 분야를 혼합하지 않는다.
- 한 신청에는 같은 인정 체계의 여러 세부 분야 Job을 포함할 수 있다.
- 관리 No.는 ISO와 K-Beauty 두 계열에서 각각 연속 부여하며 취소·오등록 번호도 재사용하지 않는다.
- 세부 분야별 Job No.와 인증번호는 각 번호 규칙 및 규칙 버전에 따라 독립 생성한다.
- 신청 단위로 대표메일 수신일, 파트너사, Dropbox 폴더, 공통서류, 서류검토를 관리한다.
- 인보이스는 여러 신청·후보자의 Job을 묶을 수 있으나 Job 하나의 비용은 한 인보이스에 전액 포함한다.
- 인증심의는 후보자별 신청 단위로 진행하며 결과는 Job별로 승인·보완·불승인을 기록한다.
- 인증서와 최종 문서 패키지는 Job별로 생성하고 여러 Job을 일괄 처리할 수 있다.
- 검토서와 인증결정보고서는 기본적으로 통합 작성하고 관련 Job들이 같은 원본을 참조한다.
- 문서전달확인서는 Job별로 생성하되 공통 전달정보를 일괄 적용할 수 있다.
- 인증서 발행일 확정 시 Word·PDF 패키지 생성 준비 상태가 되며 개별 및 ZIP 다운로드를 지원한다.
- Dropbox 자동 폴더 생성과 패키지 업로드는 후속 연동 범위로 둔다.

### 4.1 후보자

- 후보자는 Job과 분리된 독립 데이터로 관리한다.
- 후보자 한 명은 여러 인증규격의 Job을 가질 수 있다.
- 이름, 생년월일, 주소, 국적, 연락처, 이메일 등 기본정보를 관리한다.
- 주소와 연락처는 정지·철회 통보문 생성에 활용한다.

### 4.2 Job

- Job은 후보자와 인증규격의 지속적인 관리 단위이다.
- Registration No.라는 명칭은 사용하지 않고 Job No.를 사용한다.
- 인증규격마다 별도의 Job No.가 존재한다.
- 갱신이나 등급변경 시 기존 Job No.를 계속 사용한다.

### 4.3 처리 회차

- 최초, 갱신, 등급변경, 범위확대가 발생할 때마다 같은 Job 아래 새 처리 회차를 생성한다.
- 완료된 처리 회차는 과거 이력으로 고정하고 덮어쓰지 않는다.
- Job당 진행 중인 처리 회차는 최대 한 개만 허용한다.
- 기존 처리 회차가 완료되어야 갱신 또는 등급변경 회차를 시작할 수 있다.

### 4.4 권장 계층

```text
후보자
  └─ Job: 후보자 + 인증규격 + 지속되는 Job No.
       └─ 처리 회차: 최초·갱신·등급변경·범위확대
            ├─ 서류검토 회차
            ├─ 심의 회차
            ├─ 인증정보 이력
            ├─ 문서전달
            └─ 처리이력
```

## 5. 업무 상태와 전환

### 5.1 진행 상태

- DOCUMENT_REVIEW: 서류검토 대기
- DECISION_PENDING: 인증심의 대기
- SUPPLEMENT_PENDING: 보완 대기
- CERTIFICATION_INFO_PENDING: 인증정보 등록 대기
- DELIVERY_PENDING: 문서전달 대기
- COMPLETED: 처리 완료
- APPLICATION_CANCELLED: 신청 취소

### 5.2 기본 흐름

```text
처리 회차 등록
→ 서류검토
→ 인증심의
→ 인증정보 등록
→ 문서전달
→ 완료
```

### 5.3 보완과 재처리

- 서류검토가 보완필요이면 보완 대기로 전환한다.
- 심의결과가 보완이면 보완 대기로 전환한다.
- 보완자료가 접수되면 서류 재검토를 수행하고 필요한 경우 재심의한다.
- 이전 검토와 심의 결과는 수정하지 않고 회차별로 누적한다.
- 각 회차에는 순번, 결과, 의견, 실제 담당자, 양식 기재일과 시스템 감사시각을 기록한다.

## 6. 인증 상태와 사후관리

### 6.1 인증 상태

- 인증 완료
- 인증 정지
- 인증 철회
- 신청 취소

업무 진행 상태와 인증 상태는 별도 필드로 관리한다. 인증 정지와 철회는 인증 발행 이후의 사후관리 사건이며 일반 신청 상태와 혼합하지 않는다.

### 6.2 정지 및 철회 기록

- 정지 또는 철회 구분
- 대상 인증정보
- 관리번호
- 표준 사유
- 상세 사유
- 결정일과 효력 발생일
- 실제 결정자와 시스템 입력자
- 근거 문서관리번호 또는 내부 링크
- 고객의 입장
- 시정조치 검증 내용과 검증일자
- 종결 또는 인증유지 결과
- 검토자

### 6.3 사유 관리

- 관리자가 정지·철회 표준 사유를 관리한다.
- 실무자는 표준 사유를 선택하고 상세 사유를 별도로 작성한다.
- 표준 사유가 변경되어도 과거 기록에는 당시 명칭을 보존한다.

## 7. 문서관리

- 원본 신청서, 계약서, 증빙자료와 근거문서는 기존 문서관리 체계에 보관한다.
- 이 시스템에는 확인 여부, 문서관리번호, 내부 링크, 확인자, 확인일을 기록한다.
- 내부 링크는 실무자가 원본 문서로 이동하기 위한 용도이다.
- 시스템과 AI는 원본 문서를 자동으로 가져오거나 내용을 분석하지 않는다.

## 8. 업무일자 자동 계산

- 수정할 수 없는 인증발행일을 기준일로 사용한다.
- 서류검토일, 심의일, 문서전달일 등 양식 기재일은 인증발행일 앞뒤의 영업일 수식으로 자동 계산한다.
- 영업일은 토요일, 일요일, 대한민국 법정공휴일과 대체공휴일을 제외한다.
- 별도의 회사 휴일 달력은 운영하지 않는다.
- 관리자는 설정 화면에서 각 업무일자의 전·후 영업일 간격을 변경할 수 있다.
- 변경된 규칙은 변경 이후 생성되는 처리 회차에만 적용한다.
- 각 처리 회차에는 적용된 규칙 버전과 계산 결과를 보존한다.
- 시스템 입력시각은 감사용 기술정보로만 저장하고 업무 양식 날짜로 표시하지 않는다.

## 9. 담당자와 동시 편집

- 모든 실무자가 모든 Job을 공동으로 처리할 수 있다.
- Job 또는 처리 회차에 주 담당자를 지정할 수 있다.
- 주 담당자가 아니어도 업무 처리 권한을 가진다.
- 동시 조회는 허용한다.
- 동일 처리 단계의 동시 편집은 제한한다.
- 편집 중 사용자와 시작시각을 표시하고, 저장 시 데이터 버전을 확인하여 덮어쓰기를 차단한다.
- 관리자는 사유를 남기고 편집 잠금을 강제로 해제할 수 있다.

## 10. 완료, 정정과 감사로그

- 임시저장은 진행 중 기록에 허용한다.
- 완료 버튼에는 단순 확인 절차를 제공한다.
- 완료된 기록은 일반 편집을 허용하지 않는다.
- 실무자는 정정을 요청하고 관리자가 정정을 수행한다.
- 정정 대상, 변경 전 값, 변경 후 값, 정정 사유, 요청자, 처리자와 정정시각을 기록한다.
- 생성, 수정, 완료, 상태전환, 정정, 편집 잠금과 강제 해제를 감사로그에 기록한다.

## 11. 내부 알림

- 외부 이메일 알림은 제공하지 않는다.
- 모든 실무자에게 공용 내부 알림을 제공한다.
- 주 담당자가 있는 경우 알림에서 강조한다.
- 업무 연동 알림은 관련 업무가 완료되어야 자동 종료되며 사용자가 임의로 닫을 수 없다.
- 경미한 일반 안내 알림은 사용자가 읽음 또는 닫기 처리할 수 있다.
- 보완자료 접수, 단계 전환, 예정일 도래, 기한 경과, 담당자 변경과 정정 처리 등을 알림 대상으로 한다.

## 12. 보고서와 출력

### 12.1 개별 보고서

- 인증 정지·철회 보고서
- 인증 정지·철회 통보문
- 기존 FGPC-015-02 및 FGPC-015-03 Word 양식을 초기 템플릿으로 활용한다.
- 양식이 변경되면 새 템플릿 버전을 등록하고, 기존 출력물은 이전 버전을 유지한다.

### 12.2 현황 보고서

- 기간별 인증 완료, 정지, 철회, 신청 취소 현황
- 규격별·사유별 집계
- 진행 중인 갱신 Job
- 보완 대기와 기한 경과 목록

### 12.3 출력 형식

- Word: 개별 보고서 편집
- PDF: 확정 보고서 보관과 공유
- Excel: 현황 목록과 추가 분석
- PowerPoint: 월간·분기 요약 보고

## 13. 기존 Google Sheet 데이터 이전

### 13.1 이전 범위

- 과거의 모든 자료를 이전한다.
- ISO 규격, 기타 규격, K-Beauty, PJLA 등 서로 다른 시트 구조를 공통 데이터 모델로 변환한다.
- 후보자 기본정보, Job No., 인증번호, 최초 인증일, 사후관리일, 갱신일, 상태와 특이사항을 이전한다.

### 13.2 이전 원칙

- 원본 행을 변경 없이 보존하는 이전 원본 영역을 둔다.
- 원본 시트명과 행 번호를 이전 기록에 연결한다.
- 동일 후보자의 최초와 갱신 정보를 별도 처리 회차로 분리한다.
- 기존 Job No.와 인증번호는 원문 그대로 보존한다.
- AI가 동일 인물 여부를 최종 결정하지 않는다.

### 13.3 이전 검토 대기

- 명확히 일치하는 자료만 자동 통합한다.
- 중복 후보자, 상충하는 개인정보, Job No. 누락·중복과 불명확한 갱신 연결은 이전 검토 대기로 보낸다.
- 실무자는 원본 값과 변환 예정 값을 비교하고 병합, 신규 생성, 보류 또는 제외를 선택한다.
- 테스트 행과 예시 행을 제외할 때는 제외 사유를 남긴다.

## 14. 병행 운영과 완전 전환

- 병행 기간에는 Google Sheet를 공식 원본으로 유지한다.
- 새 시스템은 이전 결과와 신규 업무를 검증하는 용도로 사용한다.
- 불일치 시 Google Sheet를 기준으로 정정한다.
- 최종 전환 직전에 마지막 변경분을 증분 이전한다.
- 완전 전환 후 Google Sheet를 읽기 전용으로 바꾸고 새 시스템을 공식 원본으로 사용한다.

### 14.1 완전 전환 조건

- 전체 자료 이전과 이전 검토 대기 처리 완료
- 후보자, Job, 인증정보 건수 대조 완료
- 주요 샘플 이력 대조 완료
- 신규, 갱신, 보완, 정지, 철회 업무 테스트 완료
- Word, PDF, Excel 보고서 대조 완료
- 사용자 교육과 권한 설정 완료
- 관리자 최종 전환 승인

## 15. 권장 데이터 모델

- profiles: 사용자 프로필과 역할
- reviewers: 심의자 명단
- candidates: 후보자 기본정보
- jobs: 후보자·인증규격별 Job No.
- processing_cycles: 최초·갱신·등급변경·범위확대 처리 회차
- document_reviews: 회차별 서류검토 기록
- certification_decisions: 회차별 심의기록
- certification_records: 인증번호와 유효기간을 포함한 인증정보 이력
- document_deliveries: 문서전달 기록
- supplemental_requests: 보완 요청과 접수 기록
- certification_actions: 정지·철회 사후관리 기록
- reason_codes: 정지·철회 표준 사유
- business_day_rules: 업무일자 계산 규칙 버전
- document_references: 외부 문서관리번호와 내부 링크
- notifications: 공용 내부 알림
- corrections: 정정 요청과 변경 전후 값
- audit_logs: 모든 주요 업무 감사로그
- edit_locks: 처리 단계별 편집 잠금
- migration_sources: 원본 시트 행과 출처
- migration_reviews: 이전 검토 대기와 결정 결과
