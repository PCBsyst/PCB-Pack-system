# 개인정보 접근이력 1차 적용

1. Supabase SQL Editor에서 `supabase/migrations/202610030018_privacy_access_logs.sql` 전체를 실행합니다. 기존 테이블을 다시 생성하지 않으며 재실행 가능합니다.
2. 코드 배포 후 최고관리자 설정 화면 하단의 '개인정보 조회·문서 생성 접근이력 보기' 링크를 엽니다.
3. 실제 DB 후보자의 상세 화면을 열고 이력의 직원, 한국 기준 시각, 대상 ID를 확인합니다.
4. 실제 Word/ZIP 다운로드를 실행해 문서 생성 응답 기록을 확인합니다. 생성이나 이력 저장이 실패하면 파일을 반환하지 않습니다.
5. 활성 실무자 및 서브 관리자에게 이력 페이지 직접 접근과 `privacy_access_logs` 직접 SELECT를 시험합니다. 페이지는 거부되어야 하고 SELECT는 행을 반환하지 않아야 합니다. INSERT/UPDATE/DELETE는 일반 인증 계정에 허용되지 않습니다.

범위: DB 후보자 상세 조회, 서류검토서·인증결정보고서·문서전달확인서·정지철회 문서의 서버 생성 및 기업양식 ZIP 응답. ZIP은 내부 개별 문서 생성 기록도 남깁니다. 응답 기록은 브라우저의 실제 파일 저장이나 전달 성공 확인이 아닙니다. 고객 정보 원문은 로그에 복제하지 않습니다.

남은 범위: 목록·신청·Job 화면의 개인정보 조회, 클라이언트에서 직접 생성하는 문서 및 Excel 다운로드, 직접 DB 조회. 기존 candidates SELECT 정책은 아직 유지되므로 이번 기능을 모든 조회에 대한 강제 DB 감사라고 보아서는 안 됩니다. DB/API 경로 통합을 후속 단계에서 진행해야 합니다. 문서 대상 ID는 기존 API 입력에서 가져온 것으로, 실제 업무 대상과의 서버 조회 검증은 후속 작업입니다.

로그에는 actor_id와 서버 시각을 사용합니다. 직원 이름은 현재 profiles 명단에서 표시하므로 이름 변경 후 과거 화면의 이름도 새 이름으로 표시됩니다. UUID는 그대로 보존됩니다. 익명/비활성 사용자는 기록 RPC를 실행할 수 없습니다. 서비스 관리자의 DB 관리자 권한까지 제한하는 기능은 아닙니다.

후보자 조회 기록의 대상 칸에는 현재 후보자 이름과 상세화면 링크를 표시합니다. 고유 ID는 '추적용 ID 보기'에 보존합니다. 후보자 이름 변경 시 과거 이력의 표시 이름도 현재 이름으로 바뀌며, 후보자가 삭제되거나 조회 실패하면 이름 확인 불가로 표시하되 원래 대상 ID는 유지됩니다.
