# 신규 신청 저장 응답 점검

직원 인증을 확인한 뒤 번호를 예약한다. 신청 생성 RPC가 반환한 신청·후보자·첫 Job ID는 UUID이며, 기등록 후보자 신청이면 선택한 후보자 ID와 일치해야 한다.
담당자와 기존 인증 연결, 추가 Job 전체 입력값, 처리 회차, 관리번호 끝 범위의 저장 응답을 대조한다. 빈 응답이나 일부 행 누락을 성공으로 안내하지 않는다.
연속 클릭은 실행 중인 요청 잠금으로 제한한다. 공유·로컬 모두 저장을 확인한 뒤 화면의 등록 목록과 건수를 갱신한다.

신청 생성 요청 이후 실패하면 일부 저장이 가능하므로 해당 화면의 재등록 버튼을 막는다. 신청관리에서 신청번호로 조회하여 후보자·Job·회차·담당자 연결을 확인한다. 임의 삭제·자동 롤백·예약번호 재사용은 하지 않는다.
화면을 새로 열면 잠금은 초기화되므로 확인 없이 재등록하지 않는다. DB 차원의 영구 중복 방지나 전체 일괄 저장을 구현한 것은 아니다.

신청관리 상단의 ‘신청 저장·연결 점검’에서 특정 신청번호를 읽기 전용으로 조회한다.
공유 저장 경고의 이동 링크는 해당 신청번호를 전달하며 조회는 버튼을 눌러 실행한다.
후보자 이름·연락처·이메일을 조회하지 않고 연결 ID와 업무 정보만 사용한다. 누락된 회차, 후보자 불일치, 관리번호 범위 불일치, 담당자 미지정을 안내한다.
조회 실패는 기록 없음으로 처리하지 않는다. 원래 신청한 분야 수나 미저장 관리번호 범위는 알 수 없으므로 일치 결과가 전체 저장 완료를 보증하지는 않는다.
점검 화면은 자료를 수정·삭제하거나 신규 회차를 만들지 않는다. 기존 신청서와 대조하여 복구 여부를 결정한다.

원 신청 Job 수와 표준 목록(한 줄에 하나)을 선택적으로 입력해 실제 조회 Job과 대조할 수 있다.
공유 저장 실패 링크는 시도한 Job 수도 전달한다. 이 값은 사용자 참고값이며 DB에서 검증한 원 신청 내용이 아니다.
입력값은 서버나 브라우저 저장소에 저장하지 않으며, 표준 목록은 주소에도 넣지 않는다.
관리번호 범위가 한 건으로 남아 Job 한 건과 일치하더라도 원 신청이 두 건이라면 건수 불일치를 표시한다.
건수가 같아도 누락된 표준과 참고 목록에 없는 표준을 구분한다. 등급·증빙자료까지 확인한 것은 아니다.
대조값을 입력하지 않으면 원 신청 대비 누락 여부는 판단하지 않았다고 명시한다.

현재 신청 생성 RPC는 첫 Job까지 일괄 저장하지만 추가 Job·담당자·관리번호 범위는 별도 요청이다. 완전한 일괄 저장과 복구는 별도 DB 함수/SQL 변경 과제로 남는다. 이번 작업은 기존 DB 구조를 사용하므로 신규 SQL은 없다.
자동검사는 실제 화면 저장 함수를 실행하며 DB 응답은 모의한다. 실제 DB 권한·동시 요청·부분 저장 복구는 별도 검증이 필요하다.
## 점검 결과 안내

연결 오류나 원 신청 참고값 불일치가 하나라도 있으면 ‘확인 필요’를 우선 표시합니다. 연결 오류가 없더라도 참고값이 없으면 ‘원 신청 대조 미실시’, 건수만 입력하면 ‘건수만 대조 완료’로 구분합니다. 표준 목록까지 일치해도 등급·증빙·전체 저장 완료를 보증하지 않습니다. 문제가 발견된 기록은 자동 수정하지 않으며 신청서 대조와 관리자 확인 후 처리하도록 안내합니다.
## 번호 중복 점검

현재 신청에 속한 Job 번호를 앞뒤 공백·대소문자 차이를 제외하고 대조하여 중복된 각 Job을 확인 대상으로 표시합니다. 같은 Job의 후속 회차 번호 중복도 경고합니다. 다른 Job에 같은 회차 번호가 있는 것은 정상입니다. 원본 번호를 변경하지 않으며, 다른 신청의 Job 번호 중복은 이 점검의 대상이 아닙니다.
## 저장 전 신청번호 응답 검증

DB의 `allocate_application_number` 규칙에 맞춰 `APP-ISO-YYYY-NNN` 또는 `APP-KB-YYYY-NNN` 형식, 접수연도, 순번 001~999를 검증합니다. 응답을 임의 문자열로 변환하지 않으며 잘못된 응답이면 Job 번호 확보 및 신청 저장을 중단합니다. 실재하지 않는 접수일도 인증·번호 확보 전에 차단합니다. 기존 번호를 수정하거나 예약 번호를 재사용하지 않습니다. 번호 확보 자체는 신청 저장과 별도이므로 저장 전 실패 시에도 예약 번호가 남을 수 있습니다. 복수 Job의 원자적 저장은 아직 별도 DB 개선이 필요합니다.
## 복수 분야 사전 점검

인증·번호 확보 요청 전에 전체 신청 분야의 규칙 확정 여부와 중복 분야를 검사합니다. 갱신·등급변경은 선택한 이전 Job이 현재 화면에 조회된 이전 Job 목록에 존재하고 표준도 같은지 대조합니다. 이 화면 검증은 서버 권한·후보자 소유권 검사나 원자적 저장을 대체하지 않습니다. 설정 오류를 사전에 발견한 경우 번호 확보 요청도 보내지 않습니다.
## 기등록 후보자 전환 보호

후보자 선택·신규/기등록 모드 변경 시 이전 Job 선택을 초기화합니다. 후보자 Job 조회는 요청 순서를 대조하여 이전 요청의 늦은 응답을 무시하고 화면 종료 시에도 적용하지 않습니다. 후보자가 목록에 없으면 기존 개인정보 입력값을 비웁니다. Job은 500건씩 최대 1,000건을 분할 조회하며 건수 변경·부분 응답·중복 ID·다른 후보자 연결·조회 실패는 목록으로 확정하지 않습니다. 이는 실시간 DB 스냅샷이나 서버 소유권 검사를 보증하지 않습니다.
## 신청 선택 목록 조회

공유 DB 연결 시 후보자·활성 파트너사·활성 담당자를 500건씩 최대 10,000건까지 분할 조회합니다. 세 목록과 현재 직원의 활성 목록 포함 여부를 모두 확인한 후 화면에 적용합니다. 건수 불일치·부분 조회·손상 데이터·조회 실패는 로컬 샘플로 대체하지 않고 등록을 차단합니다. 화면 종료 후 응답은 적용하지 않습니다. 오류 안내의 목록 재조회는 후보자 입력·신청 분야·파트너사·선택 담당자를 유지하며 목록만 다시 확인합니다. 재조회 목록에서 선택 항목이 사라졌으면 등록을 차단하고 재선택을 안내합니다. 담당자 선택이 없을 때만 현재 직원으로 초기화하며, 기존 선택을 임의로 변경하지 않습니다. 실제 DB 동시 변경·RLS 검증은 별도입니다.
## 신규 후보자 개인정보 입력 점검

신규 후보자에 한해 인증·번호 예약·로컬 저장 전에 입력을 검사합니다. 이름은 필수이며 영문명·생년월일·국적·이메일·전화번호는 선택입니다. 입력한 생년월일은 실재 날짜이며 접수일 이후가 아니어야 합니다. 이메일은 기본 주소 형식만 검사하며 소유권·실제 수신 가능성을 검증하지 않습니다. 제어문자와 과도한 길이는 차단하고 오류 안내에 개인정보 원문을 포함하지 않습니다. 국제 전화번호와 내선 표현은 특정 국내 형식으로 강제하지 않습니다. 과거 기등록 후보자 정보는 자동 정정하거나 소급 검사하지 않습니다. 서버 검증을 대체하는 보안 경계는 아닙니다.
