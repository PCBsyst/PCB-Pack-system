# Supabase 연결 순서

현재 앱은 가상데이터와 브라우저 저장소로 계속 동작한다. Supabase 프로젝트가 준비되면 다음 순서로 전환한다.

1. Supabase에서 새 프로젝트를 만든다.
2. SQL Editor에서 `migrations/202609280001_initial_certification_schema.sql`을 실행한다.
3. `.env.example`을 참고해 로컬 `.env.local`과 Vercel 환경변수에 프로젝트 URL과 Publishable Key를 등록한다.
4. 관리자 계정을 이메일로 초대하고 `profiles.role`을 `ADMIN`으로 변경한다.
5. 가상데이터를 후보자, 신청, Job, 처리회차 순서로 시험 이관한다.
6. 화면별 읽기 경로를 Supabase로 먼저 전환한 뒤 저장 경로를 전환한다.
7. 병행 운영 검증이 끝날 때까지 구글 시트를 공식 원본으로 유지한다.

## 주요 관계

- 후보자 1명은 여러 신청과 여러 Job을 가질 수 있다.
- 신청 1건은 여러 Job을 가질 수 있다.
- Job 1건은 갱신이나 등급변경을 포함한 여러 처리회차를 가진다.
- 인보이스 1건은 여러 Job과 연결될 수 있다.
- 인증결정 1건에는 최소 2명의 패널 기록을 연결한다.
- 인증기록은 기존 이력을 덮어쓰지 않고 회차별로 추가한다.
- 패키지 문서는 Job 및 처리회차 기준으로 관리한다.

## 보안과 무결성

- 모든 업무 테이블에 RLS가 활성화된다.
- 활성화된 내부 직원만 조회·등록·수정할 수 있다.
- 삭제는 관리자만 가능하다.
- 주요 업무 테이블의 변경 전후 값은 `audit_logs`에 자동 기록된다.
- `record_locks`는 같은 업무건의 동시 편집을 제한하는 데 사용한다.
- 정정 사유는 DB 요청 전에 `set_config('app.correction_reason', '사유', true)`로 설정하면 감사로그에 함께 남는다.

## 아직 실행하지 않는 항목

- 실제 Supabase 프로젝트 생성과 환경변수 등록
- 운영 데이터 이관
- 화면의 브라우저 저장소 제거
- Dropbox 파일 자동 보관
