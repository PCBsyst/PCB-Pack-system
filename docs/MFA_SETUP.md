# 인증 앱 등록과 확인

상단 방패 아이콘의 ‘내 계정 보안’에서 직원 본인의 TOTP 인증 앱을 연결한다. 활성 직원만 접근하며 로컬 가상데이터 모드에서는 등록하지 않는다. 기존 DB 마이그레이션은 필요 없다.

등록은 버튼을 누를 때만 시작한다. QR 및 수동 설정 키는 컴포넌트 메모리에서만 유지하고 코드 확인 성공 시 제거한다. 페이지를 벗어나면 다시 표시하지 않는다. 미확인 등록이 남았을 때 앱에 저장한 코드로 확인할 수 있다. 자동 삭제나 자체 초기화는 제공하지 않는다.

비밀번호 로그인에서 등록된 인증 앱이 있으면 코드 입력 단계로 전환한다. 정상 코드 확인 및 현재 인증 수준 AAL2 확인 후 업무 홈으로 이동한다. 취소는 현재 세션 로그아웃을 수행한다. 인증 앱이 없는 직원은 기존 로그인 흐름을 유지한다.

2026-10-04 서버 보호 보완: Proxy, 서버 직원 조회, 문서·패키지 API, 직원 초대·정보 변경 API에서 검증된 JWT의 AAL과 Auth 서버에서 다시 조회한 verified factor를 확인한다. 등록 계정의 AAL1 업무 요청은 차단하고 인증 화면으로 안내한다. 최고관리자는 verified factor가 없으면 등록 화면으로 안내한다. 권한/인증 조회 오류와 사용자 불일치는 허용하지 않는다. 리디렉션에도 갱신된 인증 쿠키를 전달하고 인증 응답은 no-store로 처리한다.

인증 등록/확인 화면은 업무 AppShell과 분리해 업무 데이터·알림을 가져오지 않는다. 활성 직원 확인만 예외로 허용하며, 성공 후 AAL2를 확인하고 업무 이동 버튼을 표시한다. 관리자 본인이 등록을 완료해야 하는 단계는 자동으로 대신 수행하지 않는다.

한계: MFA 미등록 일반 직원은 현재 기존 접근을 유지한다. 15일 신뢰 기기를 구현하기 전 단계적 보완이며 모든 직원에게 MFA가 강제된 상태는 아니다. 직접 Supabase DB/API 접근에는 아직 이 서버 보호가 적용되지 않는다. 관리자 전용 복구 절차, 15일 신뢰 기기, 서버 세션 만료도 별도 구현·검증 대상이다. 인증 수단을 Supabase 자체 API에서 삭제하는 경로까지 관리자 전용으로 제한된 것은 아니다. 브라우저에 이미 로드된 데이터의 회수나 모든 클라이언트 화면의 재인증을 보장하지 않는다.

검증: `scripts/test-server-mfa-policy.mjs`의 정책 48개 조합, Auth 조회 실패·사용자 불일치 등 모의 응답 7건 및 보호 경로 연결 검사. 실제 Auth 서버의 인증 앱 등록·코드·쿠키 갱신·전체 권한 시험은 별도 필요하다.

후속 수동 검증: 인증 앱 등록 → 잘못된 코드 거절 → 정상 코드 승인 → 새로고침 후 등록 상태 유지 → 새 로그인 세션의 인증 수준 확인. 실제 QR/키/코드를 검증 기록이나 스크린샷에 남기지 않는다. 검증 전 실제 개인정보 운영에 투입하지 않는다.
