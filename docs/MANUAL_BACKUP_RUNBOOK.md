# 무료 수동 백업 준비 및 실행 기준

2026-10-04 백업 내보내기, 암호화 무결성 및 현재 백업 범위의 격리 DB 복원 시험을 완료했다. 파일 저장소 실파일 복구·실제 서비스 로그인·전체 역할별 권한 시험은 별도 작업이다.

## 현재 도구 상태 (2026-10-03)

- Supabase CLI 2.119.0 공식 Windows x64 ZIP을 `.tools/supabase/2.119.0/bin/supabase.exe`에 설치했다. 공식 `checksums.txt`의 SHA-256과 일치하고 `--version` 실행을 확인했다. 시스템 PATH는 변경하지 않았다.
- Docker Desktop 4.93.0을 현재 사용자 전용으로 설치했다. Docker CLI 29.8.1 실행을 확인했다. 약관 자동 동의 옵션은 사용하지 않았다.
- WSL 2.7.13.0 공식 Microsoft x64 MSI의 SHA-256을 확인하고 설치 종료 코드 0과 버전 실행을 확인했다. `/norestart`를 사용했으며 자동 재시작은 하지 않았다.
- 사용자 로그인 후 Docker 엔진 29.8.1 조회 및 공식 `hello-world` 이미지 다운로드·컨테이너 실행을 확인했다. 백업 도구 사전 점검은 준비 상태다.
- 현재 터미널의 Docker 자격증명 helper 검색 오류는 해당 프로세스에만 Docker `resources/bin`을 PATH에 추가하여 해결했다. 백업 실행 프로세스에도 이 경로가 필요하다. 시스템 PATH나 인증 보호는 변경하지 않았다.
- 실제 비밀번호 대신 가짜 문자열을 사용한 CLI `db dump --dry-run`을 확인했다. 실제 비밀번호로 dry-run/debug를 실행하면 비밀번호가 출력될 수 있으므로 금지한다.
- 2026-10-04 역할(370바이트), 구조(92,698바이트), 데이터(203,672바이트) 암호화 백업을 확인했다. 세 파일의 복호화 후 SHA-256 일치와 평문 SQL 잔존 0건을 확인했다. SQL 본문이나 고객 데이터는 출력하지 않았다.

## 복원 시험 진행 결과 (2026-10-04)

- `scripts/test-backup-restore.ps1`로 공식 Supabase PostgreSQL 17.11.0.002 이미지에서 시험했다. 외부 네트워크/공개 포트 없이 DB 데이터 디렉터리는 임시 메모리로 사용했고 시험 후 해당 컨테이너를 중지·제거했다.
- 이미지 초기화에 필요한 pg_stat_statements 사전 로드와 기본 역할을 준비했다. 로컬 시험 역할은 운영 환경 권한과 동등하다는 의미가 아니다.
- 이전 실패는 Auth·Storage 기본 테이블 누락 및 Auth 버전 차이였다. 공식 Auth v2.197.0과 Storage v1.74.0의 마이그레이션을 같은 격리 네트워크에서 실행해 해결했다. 데이터 구문을 생략하거나 가짜 테이블을 만들지 않았다.
- 역할·업무 스키마·전체 데이터 파일을 오류 발생 시 중단하는 트랜잭션으로 복원했다. 후보자/신청/Job 각 1건을 확인했고 전체 외래키 참조관계 및 핵심 4개 테이블 RLS 활성 설정 검사를 통과했다. 이 결과만으로 운영 권한 전체가 안전하다고 판단하지 않는다.
- `./scripts/test-backup-restore.ps1 -VerifyPendingMigrations`는 격리 DB에만 SQL 019~024를 순서대로 두 번 적용하고 보호 동작을 시험한다. 구형 저장 함수가 없어도 024를 적용할 수 있도록 조건부 권한 회수로 보완했다.
- 최고관리자 세션의 사유 없는 변경 거절, 올바른 정정과 버전 증가, 구버전 저장 거절, 보관/복원, 직접 삭제 거절, 오등록 삭제 및 삭제 감사기록 보존을 확인했다. 시험 입력은 롤백하며 DB 컨테이너도 제거한다. 실무자·서브 관리자·실제 로그인 세션과 전체 API 시험은 별도 필요하다.
- 운영 DB, 백업 원본은 변경하지 않았다. 019~024 마이그레이션도 미적용이다.

## 결정

- 유료 서비스는 도입하지 않는다. 자동백업, 15분 복구 목표, 2개월 보관은 아직 구현되지 않았다.
- Supabase 공식 CLI 절차로 역할(`roles.sql`), 구조(`schema.sql`), 데이터(`data.sql`)를 각각 확보한다.
- 공식 절차에는 Supabase CLI와 실행 가능한 Docker가 필요하다. 진단: `./scripts/check-backup-readiness.ps1`.
- 무료 IPv4 Session pooler를 사용한다. Transaction pooler나 유료 IPv4 추가 옵션은 사용하지 않는다.
- DB 비밀번호는 사용자가 로컬에서 직접 입력한다. 대화, 소스, 셸 명령 기록, Git, 로그에 비밀번호/전체 연결 문자열을 저장하지 않는다.
- 실제 백업은 Git 저장소 및 OneDrive/Dropbox 동기화 경로 밖의 소유자 전용 폴더에 저장한다. 권한 제한과 암호화 보관 방법을 실제로 확인한 다음 실행한다. `.gitignore`는 암호화나 권한 보호를 대신하지 않는다.

## 실행 게이트

1. 공식 배포처의 도구 설치 및 실행 상태 확인.
2. 사용자가 기존 DB 비밀번호를 안전한 로컬 입력 방식으로 제공. 필요시 비밀번호 재설정은 사용자가 직접 수행하며 기존 연결 영향도 확인.
3. 백업 기간 동안 다른 직원의 입력과 스키마 변경을 멈춘다. 세 번의 dump는 서로 다른 시점일 수 있으므로 동일 시점 스냅샷이라고 부르지 않는다.
4. 역할/구조/데이터 각각 종료 코드, 파일 크기와 SHA-256 확인. 일부 파일만 성공하면 전체 백업 완료로 처리하지 않는다.
5. 별도 시험 DB에서 복원하고 고객/신청/Job/업무 기록 및 핵심 함수·정책을 검증한다. 운영 DB에 복원하거나 기존 데이터를 덮어쓰지 않는다.
6. 최소한 변경 전 스키마와 데이터가 확보되었는지 확인한 뒤 019~024 적용 가능 여부를 판단한다. 복원 시험 미실시 사실을 별도로 표시한다.

## 별도 백업 범위

- 현재 수동 내보내기는 Storage 벡터 메타데이터(`storage.buckets_vectors`, `storage.vector_indexes`) 2개 테이블을 제외한다. 복원 성공은 보관된 세 파일의 범위에 대한 결과이며 모든 Supabase 내부 데이터 및 설정의 완전 복구를 뜻하지 않는다. 벡터 저장소를 사용하기 전 이 범위를 보완해야 한다.
- Storage 실파일, Dropbox 파일, 이메일, Vercel 환경변수, SMTP 및 인증 공급자 설정은 DB dump만으로 백업되지 않는다.
- `auth`/`storage`의 사용자 정의 트리거·정책, 마이그레이션 이력, 암호화 키는 별도 확인한다. 공식 문서의 특수 복원 사항을 따른다.
- 같은 노트북에서만 복구 가능한 암호화 방식은 외부 백업으로 간주하지 않는다. 다른 기기에서도 복원할 수 있는 키 보관 계획이 필요하다.
